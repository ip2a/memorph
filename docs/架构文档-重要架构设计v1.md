# 架构文档 — 重要架构设计 v1

> **通用规范。** 适用于"编译型语言核心(以 Rust 为范例)+ 多平台多形态分发"的项目。
> 本文以 `myapp` 作为示例项目名占位,实际使用时**替换为你自己的项目名**。
> 文中出现的 `myapp`、`myapp-cli`、`myapp-python`、`myapp-tauri`、`myapp-bin-<triple>` 均为示意命名。

---

## 1. 设计目标

- **用户只记一个名字**:`myapp`。不带任何后缀。
- **同名、多平台、多形态**:不同平台拿到的是不同完整度的产物,但**名字不变**。
- **核心与应用分离**:核心 lib 是地基,且**不感知自己被怎么交付**。
- **各平台发布内容可以不同** —— 这是有意为之,不是缺陷。按用途选平台。
- **带后缀的名字是工程内部细节**,用户不直接接触、不需要记住。

---

## 2. 核心模型

> **一个核心 lib 是地基。所有交付形态从它派生,完整度逐层递增,用户看到的名字永远是 `myapp`。**

核心 lib 只负责领域逻辑与数据/文件 IO。一切"交互形态"(命令行解析、TUI 渲染、HTTP API/Web server、桌面 GUI、MCP server)都在它之上叠加,且彼此可组合、可裁剪。

---

## 3. 完整度梯度

从最小(仅核心 API)到最完善(全功能二进制 / 桌面完全体):

```
完整度 →  低 ────────────────────────────────────────────────────────→  高

  cargo add        pip install          npx              npm i -g        curl | sh        dmg/app
  ────────────     ──────────────       ────────          ────────────    ────────────     ────────────
  核心 lib          绑定(Python 视图)   临时跑            全局装           预编译二进制      完全体发行版
  源码/API          纯库·无 CLI         CLI 或 MCP        完整 CLI         最完善            全能力 + GUI
```

**关键关系**:`curl | sh` 与 `dmg/app` 处于**同一完整度**,只是形态不同 —— 前者命令行,后者桌面 GUI,能力等价。

---

## 4. 分发渠道清单

| 层级 | 渠道 | 用户输入 | 拿到什么 | 完整度 |
|---|---|---|---|---|
| **L0 地基** | cargo | `cargo add myapp` | Rust 核心 lib(无 CLI / api / web / TUI) | 仅核心 API |
| **L1 绑定** | pip | `pip install myapp` | PyO3 Python 库(核心 API 的 Python 视图) | 核心 API(Python 投影) |
| **L2 即跑** | npx | `npx myapp …` | 基于 npm 包,临时跑 CLI 或 MCP | 完整(临时) |
| **L2 即跑** | uvx | `uvx myapp …` | 基于 pypi 包,临时跑(能力视 pypi 包设计而定,见 §7) | 视设计而定 |
| **L3 完整** | npm | `npm install -g myapp` | 全局 CLI 二进制 | 完整(≈ curl) |
| **L3 最完善** | curl | `curl -fsSL … \| sh` | 预编译全功能二进制 | 最完善 |
| **L3 完全体** | 发行版 | 下载 `.dmg` / `.msi` / `.AppImage` | **完全体**:全 CLI 能力 + GUI | 最完善(+GUI) |

> `curl | sh` 与桌面发行版**能力等价**,仅交付形态不同:一个命令行,一个 GUI。

---

## 5. 派生关系

按**四个分发平台**分叉。本图只画**平台边界**;平台内部具体提供什么,由项目按 §7 自行评估 —— 规范不写死形态。

```
【核心 lib】(Rust · 地基 · 纯领域逻辑)
    │
    ├─ ① crates.io            [cargo add]
    │    └─ 核心 lib                              ← 确定提供 · 纯库
    │
    ├─ ② pypi                 [pip install / uvx]
    │    └─ 包内容由项目自评(见 §7):
    │         纯 lib / 带 CLI 入口 / 按需子集,均可
    │
    ├─ ③ npm                  [npx / npm install -g]
    │    └─ CLI 二进制                            ← npx 即跑 / npm i -g 完整 ≈ curl
    │
    └─ ④ curl | sh            [install.sh]
         └─ 完整 CLI 二进制   ← 最完善 · 全能力
```

**桌面发行版**(独立分支,不在上述四个渠道内):

```
【桌面发行版】[GitHub Releases · dmg / app / msi / AppImage]
    └─ 完全体   ← 能力 = curl | sh,多一层 GUI(Tauri 包壳产出)
```

> **MCP 不单列**:MCP 是 **CLI 的一种**(一个子命令),不是独立分发形态。CLI 是否提供 mcp 子命令、是否默认启动它,由项目自定,规范不约束。因此上图的每个"CLI"都可能含 mcp,但不把它画成独立分支。
>
> **uvx / npx 不写死**:能跑出什么,取决于对应包里装了什么入口 —— pypi 包见 §7 三选一,项目自行设计;npm 包是 CLI 二进制。本图不给固定答案。

## 6. workspace 内部 crate 划分

| crate | 角色 | 产物 | publish |
|---|---|---|---|
| `myapp` | 核心 lib(领域逻辑 + 数据/文件 IO) | lib | ✅ crates.io |
| `myapp-cli` | bin = 核心 lib + **clap / ratatui(TUI)/ axum(api·web server)/ mcp 子命令** | 二进制 `myapp` | ❌ `false` |
| `myapp-python` | PyO3 cdylib,Python 绑定,打进 pypi wheel | cdylib | ❌ `false` |
| `myapp-tauri` | Tauri 桌面壳,依赖 `myapp-cli`(复用全能力) | .app/.dmg/.msi | ❌ `false` |
| `myapp-bin-<platform-id>` | 各平台预编译二进制 | 二进制 | npm 子包(用户不直接装) |

`<platform-id>` 不是 Rust 的 target triple,而是 npm / PyPI 风格的平台标识(见 §13.2)。平台子包名对用户不可见,只用于包管理器自动选择二进制。

> **只有核心 lib 发 crates.io。** CLI、绑定、桌面壳全部 `publish = false`,只在各自平台的打包流程里被消费。

## 7. Python 包 / uvx 的设计选择(**规范不约束,项目自评**)

### 7.1 背景:uvx 与 pypi 包的耦合

`uvx myapp` 的本质是**临时创建环境并运行 pypi 包的 `console_scripts` 入口**。

- **纯库(无入口)的 pypi 包,`uvx` 无法运行它。**
- 因此 **pypi 包的设计直接决定 uvx 的能力上限**。

这带来一个**耦合点**:pypi 包"是不是纯库"同时决定了 ① `pip install` 用户的包体积与依赖重量 ② `uvx` 能跑什么。**项目需自行评估,本规范不强制统一。**

### 7.2 三种典型选择

| 选择 | pypi 包内容 | pip 用户拿到 | uvx 表现 | 适用场景 |
|---|---|---|---|---|
| **A. 纯 lib** | 仅 Python 绑定,无 `console_scripts` | Python 库,轻 | **uvx 不可用**(无入口) | 只服务 Python 库用户;要跑 CLI 走 npx / curl |
| **B. 完整 CLI** | 绑定 + 完整 CLI 入口(tui / web / api / mcp) | Python 库 + CLI(重) | **uvx ≈ curl**(临时跑完整版) | 让 Python 生态用户能临时跑全功能 |
| **C. 按需子集** | 绑定 + 部分入口(例:仅 mcp,无 tui / web) | Python 库 + 轻量入口 | uvx 只跑包含的部分(例:只起 MCP) | 给 Python 生态提供定向入口,不背完整 CLI |

### 7.3 取舍要点(供评估)

- **A 最干净**,但放弃 uvx;跑 CLI 全走 npm / curl。
- **B 最强**,但 pip 用户背完整 CLI 的重依赖。
- **C 最灵活**,但需自行裁剪入口、维护"哪些进哪些不进"。
- 三者可演进:初期选 A,后续按需升级到 C 或 B。

> **规范态度**:uvx 渠道是否启用、启用到什么程度,**完全是项目的设计自由**,本规范只要求"无论怎么选,用户可见名仍是 `myapp`"。

## 8. 交互形态的归属

所有"交互形态"归 **`myapp-cli`**,核心 lib 不含任何一项:

| 形态 | 归属 | 说明 |
|---|---|---|
| 命令行解析(clap) | `myapp-cli` | CLI 的入口骨架 |
| TUI(ratatui/crossterm) | `myapp-cli` | 终端交互界面 |
| HTTP API / Web server(axum) | `myapp-cli` | REST + 内嵌 SPA |
| MCP server | `myapp-cli` | 作为 CLI 的一个**子命令**,不独立分发 |
| 桌面 GUI(Tauri) | `myapp-tauri` | 依赖 `myapp-cli`,复用其全部能力 |

**MCP 不是独立分发物**,它是 CLI 的一种能力(`myapp mcp …`)。跑 MCP = 跑 CLI 的 mcp 子命令,因此 `npx myapp mcp` / `uvx myapp mcp`(若启用)/ 装好后的 `myapp mcp` 都成立。

**CLI 的默认入口行为**(启动后默认进 TUI / 起 MCP server / 交互菜单 / 其他)属于**实现自由,本规范不约束**。

---

## 9. 核心 lib 的职责边界

### 9.1 原则

- 核心 lib = **领域逻辑 + 数据/文件 IO**。
- **不包含**:CLI 参数解析、TUI 渲染、HTTP server、桌面 GUI、任何"交付形态"相关代码。
- **判据**:核心 lib 能在"无任何交互前端"的环境下被直接调用并完成领域工作。

### 9.2 重依赖的处理

核心 lib 应保持依赖精简。确需的重依赖:

- 能移到 `myapp-cli` 的,一律移走(axum / ratatui / crossterm / clap 等)。
- 必须留在核心的,用 **Cargo feature 门控**(可选依赖 `optional = true`),让使用者能 `default-features = false` 甩掉。
- 这是 `cargo add myapp` 的用户**只拿到最小依赖树**的保证。

### 9.3 核心 lib 的 API 稳定性

核心 lib 是对外公开契约(crates.io 上被 `cargo add`)。其公开 API 应:

- 有意设计、有文档、有版本语义化(SemVer)。
- 不随意暴露内部实现细节。
- 跨小版本保持兼容;不兼容变更走主版本号。

> CLI / 绑定 / 桌面壳的内部结构不属于公开契约,可自由演进。

---

## 10. 铁律

1. **用户可见名永远是项目名(`myapp`)**,不带后缀。平台不同 → 形态不同 → 名字不变。
2. **带后缀的全是工程内部**(`myapp-cli` / `myapp-python` / `myapp-tauri` / `myapp-bin-<platform-id>`),`publish = false` 或作为 npm 子包,用户不直接接触。
3. **MCP / TUI / web / api 都是 `myapp-cli` 的内部能力**,不独立分发;CLI 的默认入口行为不受规范约束。
4. **桌面发行版 = 完全体**,非阉割版,能力 = `curl | sh`,只是多一层 GUI。
5. **核心 lib 不感知交付形态**:纯领域逻辑 + IO,交互形态全部在上层 crate。
6. **只有核心 lib 发 crates.io**,其余 crate `publish = false`,在各自平台打包流程内消费。
7. **版本号统一锁步**(workspace 共享 version),所有 crate 与所有平台产物同版号。

## 11. 命名与 publish 速查

| 用户可见名 | 平台 | 形态 | 工程来源(crate) |
|---|---|---|---|
| `myapp` | crates.io | Rust 核心 lib | `myapp` |
| `myapp` | pypi | Python 绑定(纯库或带入口,见 §7) | `myapp-python` (cdylib) + Python wrapper |
| `myapp` | npm | CLI 二进制 shim | `myapp-cli` 编译产物 → `myapp-bin-<platform-id>` 子包 |
| `myapp`(命令) | `curl \| sh` | 全功能预编译二进制 | `myapp-cli` 编译产物 |
| `myapp.app` 等 | GitHub Releases | 桌面发行版 | `myapp-tauri` 打包 |

**内部 crate 一律不出现在用户视野**:

| 内部 crate | publish | 被谁消费 |
|---|---|---|
| `myapp` | ✅ crates.io | Rust 用户 + 其他内部 crate |
| `myapp-cli` | ❌ false | npm 打包 / curl 打包 / Tauri 壳 |
| `myapp-python` | ❌ false | pypi 打包 |
| `myapp-tauri` | ❌ false | 桌面发行版打包 |
| `myapp-bin-<platform-id>` | npm 子包 | npm 主包 shim 按平台拉取 |

## 12. 包名注册、后缀与可信发布

> 本节把§10、§11的命名规则落到**可执行的注册与发布配置**。`myapp` 为占位项目名,实际替换为你的项目名。

### 12.1 包名注册(占名与归属)

#### crates.io
- 使用 `cargo publish` 前需在 crates.io 创建账号,并生成 API token。
- 注册先到先得;发布前用 `cargo search myapp` 确认是否被占用。
- **当前 crates.io 不支持 OIDC 可信发布**,发布时仍需把 token 存为 GitHub repository/organization secret(通常是 `CARGO_REGISTRY_TOKEN`),由 CI 调用 `cargo publish`。

#### PyPI
- 访问 [pypi.org/manage/account/publishing](https://pypi.org/manage/account/publishing) 添加 **Trusted Publisher**。
- 选择 publisher 类型为 GitHub,绑定组织/仓库、workflow 文件名、可选 environment。
- 绑定后,GitHub Actions 不再依赖长期 token,而是临时用 OIDC token 换取 PyPI 上传权限。
- 包名同样先到先得;`pip index versions myapp` 或 PyPI 搜索页可确认占用。

#### npm
- 若使用裸名(`myapp`),直接在 [npmjs.com](https://www.npmjs.com/) 注册/登录后 publish;全局唯一,先到先得。
- 若担心抢注或需要团队协作,使用 scoped 名(`@myorg/myapp`):
  - scope 下的包名由组织自行管理,不会被外部占用。
  - scoped 主包的子包也自动归该 scope(如 `@myorg/myapp-bin-darwin-arm64`)。
- npm 于 2024 年支持 **Trusted Publishing**(OIDC)。在 npm 包的 Access 设置里绑定 GitHub 仓库、workflow、environment 后即可取消长期 token。

#### 用户可见名一致
- 无论内部 crate/子包叫什么后缀,**发布到各平台的主包名统一为 `myapp`**(或你的 scope 名 `@myorg/myapp`),不带 `-cli`、`-python`、`-bin-*` 后缀。

### 12.2 平台子包后缀设计(`<platform-id>`)

#### 不是 Rust triple
规范里出现的后缀是 **`<os>-<arch>[-<abi/libc>]`**,不是 Rust target triple:

| 错误(Rust triple) | 正确(platform-id) | 原因 |
|---|---|---|
| `x86_64-apple-darwin` | `darwin-x64` | npm 的 `os`/`cpu` 字段用 `darwin` + `x64` |
| `aarch64-apple-darwin` | `darwin-arm64` | npm 的 `cpu` 字段用 `arm64` |
| `x86_64-unknown-linux-gnu` | `linux-x64-gnu` | 需区分 glibc 与 musl 预留位 |
| `aarch64-unknown-linux-gnu` | `linux-arm64-gnu` | 同上 |
| `x86_64-pc-windows-msvc` | `win32-x64-msvc` | npm `os` 为 `win32`;保留 msvc 为 mingw 留位 |

#### 字段约定
| 字段 | 取值示例 | 说明 |
|---|---|---|
| `<os>` | `darwin`、`linux`、`win32` | 与 npm `os` 字段保持一致 |
| `<arch>` | `arm64`、`x64` | npm `cpu` 字段风格;不用 `aarch64`、`x86_64` |
| `<abi/libc>` | `gnu`、`msvc` | 必要时加,为后续 `musl`、`mingw` 等变体留位 |

#### 最小平台清单(按需扩展)
| 平台 | `<platform-id>` | npm `os` | npm `cpu` | PyPI marker(片段) |
|---|---|---|---|---|
| macOS Apple Silicon | `darwin-arm64` | `darwin` | `arm64` | `platform_system=='Darwin' and platform_machine=='arm64'` |
| macOS Intel | `darwin-x64` | `darwin` | `x64` | `platform_system=='Darwin' and platform_machine=='x86_64'` |
| Linux x86_64 glibc | `linux-x64-gnu` | `linux` | `x64` | `platform_system=='Linux' and platform_machine=='x86_64'` |
| Linux arm64 glibc | `linux-arm64-gnu` | `linux` | `arm64` | `platform_system=='Linux' and platform_machine=='aarch64'` |
| Windows x64 MSVC | `win32-x64-msvc` | `win32` | `x64` | `platform_system=='Windows' and platform_machine=='AMD64'` |

### 12.3 跨平台分发机制

#### npm: `optionalDependencies` + `os`/`cpu`
主包不直接放二进制,而是声明所有平台的子包为 `optionalDependencies`:

```json
{
  "name": "myapp",
  "optionalDependencies": {
    "myapp-bin-darwin-arm64": "0.1.0",
    "myapp-bin-darwin-x64": "0.1.0",
    "myapp-bin-linux-x64-gnu": "0.1.0",
    "myapp-bin-linux-arm64-gnu": "0.1.0",
    "myapp-bin-win32-x64-msvc": "0.1.0"
  }
}
```

每个平台子包在自己的 `package.json` 中声明:

```json
{
  "name": "myapp-bin-darwin-arm64",
  "os": ["darwin"],
  "cpu": ["arm64"]
}
```

npm install 时,**只下载匹配当前 `os` + `cpu` 的子包**,其余子包因 platform mismatch 被忽略(optional 保证不会报错)。

#### PyPI: 环境 marker
主包的 `pyproject.toml` 用 `platform_system` + `platform_machine` 环境 marker 按平台拉子包:

```toml
[project]
name = "myapp"
dependencies = [
  "myapp-bin-darwin-arm64==0.1.0; platform_system=='Darwin' and platform_machine=='arm64'",
  "myapp-bin-darwin-x64==0.1.0; platform_system=='Darwin' and platform_machine=='x86_64'",
  "myapp-bin-linux-x64-gnu==0.1.0; platform_system=='Linux' and platform_machine=='x86_64'",
  "myapp-bin-linux-arm64-gnu==0.1.0; platform_system=='Linux' and platform_machine=='aarch64'",
  "myapp-bin-win32-x64-msvc==0.1.0; platform_system=='Windows' and platform_machine=='AMD64'",
]
```

pip/uv 安装时,**只保留匹配当前平台的 marker**,只下载对应的平台子包。

### 12.4 可信发布(Trusted Publishing)

#### 通用骨架
所有 OIDC 可信发布都需要 CI 里三处配合:

1. workflow 顶部声明 `permissions: id-token: write`
2. job 声明 `environment: <name>`(可选但强烈建议,可在包管理平台侧限定到特定环境)
3. job 内不再使用长期 token,由官方 action(或自定义 OIDC 请求)换取临时凭证

#### PyPI Trusted Publishers
在 PyPI 仓库的 **Publishing** 设置中添加 publisher:
- Publisher: GitHub
- Owner/Repository: `myorg/myapp`
- Workflow name: `release-publish-pypi.yml`
- Environment name: `pypi`(可选,但建议)

CI 中不再需要 `PYPI_API_TOKEN`,改用 `pypa/gh-action-pypi-publish` 即可:

```yaml
permissions:
  id-token: write

jobs:
  publish:
    runs-on: ubuntu-latest
    environment: pypi
    steps:
      - uses: actions/checkout@v4
      - uses: pypa/gh-action-pypi-publish@release/v1
```

#### npm Trusted Publishing(2024)
在 npm 包的 **Access → Trusted Publishers** 中绑定:
- Publisher: GitHub Actions
- Repository: `myorg/myapp`
- Workflow: `release-publish-npm.yml`
- Environment: `npm`(可选)

CI 中用 `actions/setup-node` 的 registry-url + `NODE_AUTH_TOKEN` 为 OIDC token:

```yaml
permissions:
  id-token: write

jobs:
  publish:
    runs-on: ubuntu-latest
    environment: npm
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: "20"
          registry-url: "https://registry.npmjs.org"
      - run: npm publish --provenance --access public
        env:
          NODE_AUTH_TOKEN: ${{ steps.id-token.outputs.token }}
```

npm 同时支持 `--provenance`,发布时会附带 GitHub Actions 的来源证明(由 npm registry 展示)。

#### crates.io(当前限制)
crates.io **尚未支持 OIDC 可信发布**,必须沿用长期 API token:
- 在 crates.io 生成 token,存为 GitHub secret(`CARGO_REGISTRY_TOKEN`)。
- CI 中执行 `cargo publish --token ${{ secrets.CARGO_REGISTRY_TOKEN }}`。
- 建议 token 权限最小化(仅允许 publish/update,不授予 yank 等权限),并设置过期时间。

#### 额外加固(可选)
- **npm provenance**:已含在 npm Trusted Publishing 流程中,`npm publish --provenance`。
- **PyPI sigstore**:PyPI 已自动为每个文件生成 sigstore 签名,无需额外配置。
- **GitHub Release artifact 签名**:可用 `sigstore/cosign` 或 SLSA generator 对二进制/安装包签名,在 release note 中贴出校验和与签名。

### 12.5 速查:哪些平台用可信发布

| 平台 | 可信发布(OIDC) | 当前推荐凭证方式 |
|---|---|---|
| PyPI | ✅ 已支持 | Trusted Publisher,无长期 token |
| npm | ✅ 2024 起支持 | Trusted Publisher + `--provenance` |
| crates.io | ❌ 暂不支持 | 长期 API token(secret) |
