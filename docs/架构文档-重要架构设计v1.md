# 架构文档 — 重要架构设计 v1

> **通用规范。** 适用于"编译型语言核心(以 Rust 为范例)+ 多平台多形态分发"的项目。
> 本文以 `myapp` 作为示例项目名占位,实际使用时**替换为你自己的项目名**。
> 文中出现的 `myapp`、`myapp-cli`、`myapp-python`、`myapp-tauri`、`myapp-bin-<triple>` 均为示意命名。

---

## 1. 设计目标

- **用户只记一个名字**:`myapp`。不带任何后缀。
- **同名、多平台、多形态**:不同平台拿到的是不同完整度的产物,但**名字不变**。
- **核心与应用分离**:核心 lib 是地基,且**不感知自己被怎么交付**。
- **各平台发布内容可以不同** —— 这是有意为之,不是缺陷。按用途选平台。
- **带后缀的名字是工程内部细节**,用户不直接接触、不需要记住。

---

## 2. 核心模型

> **一个核心 lib 是地基。所有交付形态从它派生,完整度逐层递增,用户看到的名字永远是 `myapp`。**

核心 lib 只负责领域逻辑与数据/文件 IO。一切"交互形态"(命令行解析、TUI 渲染、HTTP API/Web server、桌面 GUI、MCP server)都在它之上叠加,且彼此可组合、可裁剪。

---

## 3. 完整度梯度

从最小(仅核心 API)到最完善(全功能二进制 / 桌面完全体):

```
完整度 →  低 ────────────────────────────────────────────────────────→  高

  cargo add        pip install          npx              npm i -g        curl | sh        dmg/app
  ────────────     ──────────────       ────────          ────────────    ────────────     ────────────
  核心 lib          绑定(Python 视图)   临时跑            全局装           预编译二进制      完全体发行版
  源码/API          纯库·无 CLI         CLI 或 MCP        完整 CLI         最完善            全能力 + GUI
```

**关键关系**:`curl | sh` 与 `dmg/app` 处于**同一完整度**,只是形态不同 —— 前者命令行,后者桌面 GUI,能力等价。

---

## 4. 分发渠道清单

| 层级 | 渠道 | 用户输入 | 拿到什么 | 完整度 |
|---|---|---|---|---|
| **L0 地基** | cargo | `cargo add myapp` | Rust 核心 lib(无 CLI / api / web / TUI) | 仅核心 API |
| **L1 绑定** | pip | `pip install myapp` | PyO3 Python 库(核心 API 的 Python 视图) | 核心 API(Python 投影) |
| **L2 即跑** | npx | `npx myapp …` | 基于 npm 包,临时跑 CLI 或 MCP | 完整(临时) |
| **L2 即跑** | uvx | `uvx myapp …` | 基于 pypi 包,临时跑(能力视 pypi 包设计而定,见 §7) | 视设计而定 |
| **L3 完整** | npm | `npm install -g myapp` | 全局 CLI 二进制 | 完整(≈ curl) |
| **L3 最完善** | curl | `curl -fsSL … \| sh` | 预编译全功能二进制 | 最完善 |
| **L3 完全体** | 发行版 | 下载 `.dmg` / `.msi` / `.AppImage` | **完全体**:全 CLI 能力 + GUI | 最完善(+GUI) |

> `curl | sh` 与桌面发行版**能力等价**,仅交付形态不同:一个命令行,一个 GUI。

---

## 5. 派生关系

按**四个分发平台**分叉。本图只画**平台边界**;平台内部具体提供什么,由项目按 §7 自行评估 —— 规范不写死形态。

```
【核心 lib】(Rust · 地基 · 纯领域逻辑)
    │
    ├─ ① crates.io            [cargo add]
    │    └─ 核心 lib                              ← 确定提供 · 纯库
    │
    ├─ ② pypi                 [pip install / uvx]
    │    └─ 包内容由项目自评(见 §7):
    │         纯 lib / 带 CLI 入口 / 按需子集,均可
    │
    ├─ ③ npm                  [npx / npm install -g]
    │    └─ CLI 二进制                            ← npx 即跑 / npm i -g 完整 ≈ curl
    │
    └─ ④ curl | sh            [install.sh]
         └─ 完整 CLI 二进制   ← 最完善 · 全能力
```

**桌面发行版**(独立分支,不在上述四个渠道内):

```
【桌面发行版】[GitHub Releases · dmg / app / msi / AppImage]
    └─ 完全体   ← 能力 = curl | sh,多一层 GUI(Tauri 包壳产出)
```

> **MCP 不单列**:MCP 是 **CLI 的一种**(一个子命令),不是独立分发形态。CLI 是否提供 mcp 子命令、是否默认启动它,由项目自定,规范不约束。因此上图的每个"CLI"都可能含 mcp,但不把它画成独立分支。
>
> **uvx / npx 不写死**:能跑出什么,取决于对应包里装了什么入口 —— pypi 包见 §7 三选一,项目自行设计;npm 包是 CLI 二进制。本图不给固定答案。

## 6. workspace 内部 crate 划分

| crate | 角色 | 产物 | publish |
|---|---|---|---|
| `myapp` | 核心 lib(领域逻辑 + 数据/文件 IO) | lib | ✅ crates.io |
| `myapp-cli` | bin = 核心 lib + **clap / ratatui(TUI)/ axum(api·web server)/ mcp 子命令** | 二进制 `myapp` | ❌ `false` |
| `myapp-python` | PyO3 cdylib,Python 绑定,打进 pypi wheel | cdylib | ❌ `false` |
| `myapp-tauri` | Tauri 桌面壳,依赖 `myapp-cli`(复用全能力) | .app/.dmg/.msi | ❌ `false` |
| `myapp-bin-<triple>` | 各平台预编译二进制 | 二进制 | npm 子包(用户不直接装) |

> **只有核心 lib 发 crates.io。** CLI、绑定、桌面壳全部 `publish = false`,只在各自平台的打包流程里被消费。

---

## 7. Python 包 / uvx 的设计选择(**规范不约束,项目自评**)

### 7.1 背景:uvx 与 pypi 包的耦合

`uvx myapp` 的本质是**临时创建环境并运行 pypi 包的 `console_scripts` 入口**。

- **纯库(无入口)的 pypi 包,`uvx` 无法运行它。**
- 因此 **pypi 包的设计直接决定 uvx 的能力上限**。

这带来一个**耦合点**:pypi 包"是不是纯库"同时决定了 ① `pip install` 用户的包体积与依赖重量 ② `uvx` 能跑什么。**项目需自行评估,本规范不强制统一。**

### 7.2 三种典型选择

| 选择 | pypi 包内容 | pip 用户拿到 | uvx 表现 | 适用场景 |
|---|---|---|---|---|
| **A. 纯 lib** | 仅 Python 绑定,无 `console_scripts` | Python 库,轻 | **uvx 不可用**(无入口) | 只服务 Python 库用户;要跑 CLI 走 npx / curl |
| **B. 完整 CLI** | 绑定 + 完整 CLI 入口(tui / web / api / mcp) | Python 库 + CLI(重) | **uvx ≈ curl**(临时跑完整版) | 让 Python 生态用户能临时跑全功能 |
| **C. 按需子集** | 绑定 + 部分入口(例:仅 mcp,无 tui / web) | Python 库 + 轻量入口 | uvx 只跑包含的部分(例:只起 MCP) | 给 Python 生态提供定向入口,不背完整 CLI |

### 7.3 取舍要点(供评估)

- **A 最干净**,但放弃 uvx;跑 CLI 全走 npm / curl。
- **B 最强**,但 pip 用户背完整 CLI 的重依赖。
- **C 最灵活**,但需自行裁剪入口、维护"哪些进哪些不进"。
- 三者可演进:初期选 A,后续按需升级到 C 或 B。

> **规范态度**:uvx 渠道是否启用、启用到什么程度,**完全是项目的设计自由**,本规范只要求"无论怎么选,用户可见名仍是 `myapp`"。

## 8. 交互形态的归属

所有"交互形态"归 **`myapp-cli`**,核心 lib 不含任何一项:

| 形态 | 归属 | 说明 |
|---|---|---|
| 命令行解析(clap) | `myapp-cli` | CLI 的入口骨架 |
| TUI(ratatui/crossterm) | `myapp-cli` | 终端交互界面 |
| HTTP API / Web server(axum) | `myapp-cli` | REST + 内嵌 SPA |
| MCP server | `myapp-cli` | 作为 CLI 的一个**子命令**,不独立分发 |
| 桌面 GUI(Tauri) | `myapp-tauri` | 依赖 `myapp-cli`,复用其全部能力 |

**MCP 不是独立分发物**,它是 CLI 的一种能力(`myapp mcp …`)。跑 MCP = 跑 CLI 的 mcp 子命令,因此 `npx myapp mcp` / `uvx myapp mcp`(若启用)/ 装好后的 `myapp mcp` 都成立。

**CLI 的默认入口行为**(启动后默认进 TUI / 起 MCP server / 交互菜单 / 其他)属于**实现自由,本规范不约束**。

---

## 9. 核心 lib 的职责边界

### 9.1 原则

- 核心 lib = **领域逻辑 + 数据/文件 IO**。
- **不包含**:CLI 参数解析、TUI 渲染、HTTP server、桌面 GUI、任何"交付形态"相关代码。
- **判据**:核心 lib 能在"无任何交互前端"的环境下被直接调用并完成领域工作。

### 9.2 重依赖的处理

核心 lib 应保持依赖精简。确需的重依赖:

- 能移到 `myapp-cli` 的,一律移走(axum / ratatui / crossterm / clap 等)。
- 必须留在核心的,用 **Cargo feature 门控**(可选依赖 `optional = true`),让使用者能 `default-features = false` 甩掉。
- 这是 `cargo add myapp` 的用户**只拿到最小依赖树**的保证。

### 9.3 核心 lib 的 API 稳定性

核心 lib 是对外公开契约(crates.io 上被 `cargo add`)。其公开 API 应:

- 有意设计、有文档、有版本语义化(SemVer)。
- 不随意暴露内部实现细节。
- 跨小版本保持兼容;不兼容变更走主版本号。

> CLI / 绑定 / 桌面壳的内部结构不属于公开契约,可自由演进。

---

## 10. 铁律

1. **用户可见名永远是项目名(`myapp`)**,不带后缀。平台不同 → 形态不同 → 名字不变。
2. **带后缀的全是工程内部**(`myapp-cli` / `myapp-python` / `myapp-tauri` / `myapp-bin-<triple>`),`publish = false` 或作为 npm 子包,用户不直接接触。
3. **MCP / TUI / web / api 都是 `myapp-cli` 的内部能力**,不独立分发;CLI 的默认入口行为不受规范约束。
4. **桌面发行版 = 完全体**,非阉割版,能力 = `curl | sh`,只是多一层 GUI。
5. **核心 lib 不感知交付形态**:纯领域逻辑 + IO,交互形态全部在上层 crate。
6. **只有核心 lib 发 crates.io**,其余 crate `publish = false`,在各自平台打包流程内消费。
7. **版本号统一锁步**(workspace 共享 version),所有 crate 与所有平台产物同版号。

## 11. 命名与 publish 速查

| 用户可见名 | 平台 | 形态 | 工程来源(crate) |
|---|---|---|---|
| `myapp` | crates.io | Rust 核心 lib | `myapp` |
| `myapp` | pypi | Python 绑定(纯库或带入口,见 §7) | `myapp-python` (cdylib) + Python wrapper |
| `myapp` | npm | CLI 二进制 shim | `myapp-cli` 编译产物 → `myapp-bin-<triple>` 子包 |
| `myapp`(命令) | `curl \| sh` | 全功能预编译二进制 | `myapp-cli` 编译产物 |
| `myapp.app` 等 | GitHub Releases | 桌面发行版 | `myapp-tauri` 打包 |

**内部 crate 一律不出现在用户视野**:

| 内部 crate | publish | 被谁消费 |
|---|---|---|
| `myapp` | ✅ crates.io | Rust 用户 + 其他内部 crate |
| `myapp-cli` | ❌ false | npm 打包 / curl 打包 / Tauri 壳 |
| `myapp-python` | ❌ false | pypi 打包 |
| `myapp-tauri` | ❌ false | 桌面发行版打包 |
| `myapp-bin-<triple>` | npm 子包 | npm 主包 shim 按平台拉取 |
